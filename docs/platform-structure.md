# Platform Structure: 11ty + Netlify + GitHub

## Overview

This archive will be a static site generated by Eleventy (11ty), deployed on Netlify, with content and code stored in a GitHub repository.

- 11ty: turns templates + content into a static site.
- GitHub: single source of truth for code, content, and docs.
- Netlify: builds the site on every commit and serves the static output.

The goal is to keep the system simple, text‑first, and friendly to incremental archival work.

## 11ty basics

### Input and output

- Input directory: `src/`
- Output directory: `/_site` (default, can be changed in `.eleventy.js`)
- Netlify will build `/_site` on every deploy.

11ty reads:

- templates: `.njk`, `.md`, `.html`, etc.
- content: Markdown + front matter.
- data: JSON / JS in `_data/`.
- layouts and partials: `_includes/`.

### Content as collections

Archive content lives in `src/content/`:

```text
src/content/
  identity/
  work/
  consumption/
  creation/
  accumulation/
```

Within each, content files (Markdown or JSON) represent items, subcollections, or index pages. Front matter fields should align with the schemas defined in `docs/content-model.md`.

Examples:

```text
src/content/consumption/films/2026-001-in-the-mood-for-love.md
src/content/consumption/coffee/2026-004-sey-bensa.md
src/content/work/projects/thesis-archive-interface.md
```

11ty collections:

- Define one collection per series (identity, work, consumption, creation, accumulation).
- Optionally define collections per item type (films, books, coffee, ephemera, etc.).
- Use tags or directory-based collections to group content for browsing views.

### Templates and layouts

- `_includes/layouts/base.njk` — base HTML shell.
- `_includes/layouts/series.njk` — common pattern for category interiors.
- `_includes/layouts/item.njk` — base layout for item inspection views.
- `_includes/partials/` — header, footer, desk objects, metadata blocks, etc.

11ty uses front matter to pick layouts:

```yaml
***
layout: series.njk
series: consumption
subcollection: films
title: "Film log"
***
```

## GitHub

### Role of GitHub

GitHub is the canonical home for:

- code (templates, JS, CSS)
- content (Markdown / JSON)
- docs (`docs/`)
- Netlify config (`netlify.toml`)
- 11ty config (`.eleventy.js`)

All changes flow through Git commits, which makes the archive versioned by default.

### Branch strategy

Simple recommended setup:

- `main`: deploys to production Netlify site.
- `dev` (optional): for experiments before merging into `main`.

Netlify can be configured to deploy previews for pull requests so you can see changes before merging.

### Content editing workflow

- Add or edit content files in `src/content/...`.
- Commit changes to Git with meaningful messages.
- Push to GitHub; Netlify picks up the commit and rebuilds.

Because content is text files in Git, the archive is:

- versioned
- diffable
- portable

## Netlify

### Build settings

Netlify core concepts:

- Build command: installs dependencies and runs 11ty.
- Publish directory: where the static files live (11ty output).

Typical `netlify.toml`:

```toml
[build]
  command = "npm run build"
  publish = "_site"

[build.environment]
  NODE_VERSION = "20"

[[redirects]]
  from = "/admin/*"
  to = "/admin/index.html"
  status = 200
```

`npm run build` should run 11ty:

```json
{
  "scripts": {
    "build": "ELEVENTY_ENV=production npx @11ty/eleventy",
    "dev": "npx @11ty/eleventy --serve"
  }
}
```

Netlify behavior:

- On every push to `main`, Netlify:
  - pulls from GitHub
  - runs `npm install`
  - runs `npm run build`
  - serves `_site/`

### Deploy previews

If enabled:

- every pull request to `main` gets its own preview URL
- allows reviewing archive changes visually before merging

This is useful for bigger changes to browse systems or layout.

## How it all fits together

1. **Local editing**
   - You edit Markdown, JSON, and templates under `src/` and docs under `docs/`.
   - You run `npm run dev` locally to preview at `http://localhost:8080`.

2. **Commit to GitHub**
   - Once changes look right, you commit to the repo and push.

3. **Netlify build**
   - Netlify observes the new commit, rebuilds the site with 11ty, and deploys the static `_site/` folder.

4. **Public site**
   - Visitors see the updated archive at the Netlify URL (optionally with custom domain).

5. **Long-term archival behavior**
   - Every change is tracked in Git history.
   - You can see when items were added or updated.
   - You can branch and experiment without disrupting the main archive.

## Where the docs fit

This `docs/` directory is intentionally not part of the 11ty output. It contains:

- conceptual guidance (`site-concept.md`)
- IA (`information-architecture.md`)
- content model (`content-model.md`)
- ingest workflow (`archive-ingest-workflow.md`)
- rendering strategy (`rendering-strategy.md`)
- roadmap (`roadmap.md`)
- implementation notes (`platform-structure.md`)
- admin interface (`admin-interface.md`)
- decisions (`decisions.md`)

These files are for humans and for AI assistants; they guide how 11ty templates, content files, and Netlify configuration should evolve, but they are not rendered as public pages unless explicitly wired into 11ty.

---

## Key conventions to respect

- Keep all public pages generated by 11ty from `src/`.
- Keep all long-form project notes, decisions, and instructions in `docs/`.
- Never commit the build output directory (`_site/`) to Git; it is a build artifact.
- Use front matter in content files to match the schemas defined in `docs/content-model.md`.
- Keep Netlify configuration (`netlify.toml`) in the repo so infra is versioned alongside code and content.

## Admin item-entry page

The project should eventually include an admin-facing item-entry page so new archive records can be added without directly editing repository files.

This page should likely live outside the public archive flow, for example:
- `/admin/`
- `/studio/`
- `/archive-entry/`

Its purpose is to create or update content records that Eleventy later builds into the public site.

Possible implementation paths:
- Netlify CMS / Decap CMS connected to GitHub
- a custom protected form that writes to GitHub via API
- a lightweight internal content editor that creates Markdown/JSON records matching the archive schema

Requirements:
- compatible with GitHub as source of truth
- compatible with Netlify deployment flow
- writes records in the format expected by 11ty
- supports drafts and incomplete metadata
- supports asset upload / reference
